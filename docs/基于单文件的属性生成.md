# 全局的 field api 方案（v0.11 已实现）

> 与旧标记 api（`ducks!` / `#[duck_mod]` / `#[duck]`）共存。区别：旧 api 在 struct 所在作用域生成
> trait，跨文件引用需要路径限定；本方案把 trait 集中声明到一个模块，全 crate 每个字段名只有一个 trait。

1. 在约定的 `_fields` 模块中集中声明 trait

   ```rust
   // src/_fields.rs（lib.rs 里写 `mod _fields;`）
   use duck_trait::fields;

   fields!(
   	value,
   	pub name,
   )

   // 展开后得到以下代码
   pub(crate) trait _Value<T> {
     fn value(&self) -> &T;
     fn value_set(&mut self, v: T);
     fn value_mut(&mut self) -> &mut T;
   }

   pub trait _Name<T> {
     fn name(&self) -> &T;
     fn name_set(&mut self, v: T);
     fn name_mut(&mut self) -> &mut T;
   }
   ```

   - 名字不带 `pub` 时默认 `pub(crate)`；带任意限定符（`pub`、`pub(super)`、…）则应用到对应 trait。
   - 命名约定与标记 api 完全一致：`value` -> `_Value<T>`，getter 保持原始拼写（`r#type` -> `r#type()`，
     setter 为 `type_set`）。
   - 宏无法校验自己是否真的放在 `_fields` 模块里——放错位置只会在 `#[props]` 的 impl 处报
     unresolved trait，报错位置即 struct 文件。

2. 在 trait 声明文件中绑定

   ```rust
   // src/my-trait.rs
   #[props(value: i32)]
   pub trait My {}

   // 展开后（路径完全限定，无需 use，不会与文件内已有 import 冲突）
   pub trait My: crate::_fields::_Value<i32> {}
   ```

   - 每个 `name: Type` 对追加一个 supertrait bound，默认方法里可直接调用访问器。
   - 可选 `#[props(path = crate::my_fields, value: i32)]` 覆盖声明所在模块。

3. 在 struct 文件中实现

   ```rust
   // src/foo.rs
   #[props]
   struct Foo {
     #[prop]
     value: i32,
   }

   // 展开后
   struct Foo {
     value: i32,
   }
   impl crate::_fields::_Value<i32> for Foo {
     fn value(&self) -> &i32 {
       &self.value
     }
     fn value_set(&mut self, v: i32) {
       self.value = v;
     }
     fn value_mut(&mut self) -> &mut i32 {
       &mut self.value
     }
   }
   ```

   - `#[prop]` 是 `#[props]` 的 inert helper：字段上的标记不会独立展开（编译器本就不允许在字段上
     挂 proc-macro attribute），脱离 `#[props]` 使用只会得到编译错误，不会静默失效。
   - `#[prop]` 不接受参数（`#[prop(pub)]` 报错）；同一字段重复标记报错。
   - struct 的泛型与 where 子句照常处理：`#[props] struct Wrapper<T: Clone> { #[prop] inner: T }`
     生成 `impl<T: Clone> crate::_fields::_Inner<T> for Wrapper<T>`。

## 设计要点

- **默认路径 `crate::_fields`**：Rust/Cargo 没有把项目级配置传给 proc macro 的官方通道
  （`.cargo/config.toml` 的 `[env]` 在 stable 上无增量编译追踪保障），因此采用宏参数覆盖：
  `#[props(path = crate::my_fields)]`，默认约定 `crate::_fields`。
- **单一事实来源**：字段名要在 `fields!` 与 struct 字段各写一遍；漏声明时报错出现在 struct 的
  impl 处，声明列表即契约。
- **与旧 api 共存**：`#[prop]` 标记与 `#[duck]`/`#[_duck]` 互不干扰；但同一作用域内不要混用两套
  同名字段标记（方法解析会歧义，如 `ducks!` 在 crate 根生成过 `_Value` 时，新 api 的方法调用
  需显式 `use crate::_fields::_Value`）。
- **暂不支持**：`#[duck(MyTrait<_>)]` 自动 impl 的等价物、块级作用域 struct（函数体内）。
- 已知限制：`#[prop]` 字段同时被 `#[cfg]` 整体移除时，生成的 impl 会引用不存在的字段而报错
  （旧 api `#[duck]` 行为相同）。
